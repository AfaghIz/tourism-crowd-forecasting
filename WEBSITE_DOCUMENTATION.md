# Istanbul Crowd Compass — Build, How It Works, and Future Roadmap

This document explains how the current website prototype works, where the forecasting logic lives today, and what the next iteration should add.

## 1) What you currently built (high level)

`d-tourism-crowd-forecasting` contains two main parts:

1. A **frontend prototype** (under `frontend/`) called **Istanbul Crowd Compass**.
   - Users can select a **hotel**, **a point on the map**, or use **current location**.
   - The app shows the selection as a marker on a Leaflet map and updates a “selection chip” in the UI.
   - Searches for hotels and landmarks are powered by a **mock data layer** (so the UI works even before real APIs exist).
2. A **forecasting/modeling workflow** (under `notebooks/` and `data/`).
   - Notebooks generate processed CSV datasets and train a **Random Forest** baseline model to predict a weekly **crowd index** for Istanbul using time-based features plus demand/weather signals.
3. A placeholder backend folder (`backend/app.py`) that is currently empty.

So: the website UI is real and interactive, but the forecasting + real data wiring is not yet connected to the UI.

## 2) Frontend: how it’s built

### Tech stack

- `frontend/` is a **Vite + TypeScript** project.
- Map rendering uses **Leaflet** (`leaflet` + `leaflet/dist/leaflet.css`).
- The UI is implemented in `frontend/src/main.ts` using plain DOM APIs (not React rendering).
- Styling lives in `frontend/src/app.css` (the main prototype theme).

### Where the app starts

The app entrypoint is:

- `frontend/index.html`
  - Loads `/src/main.ts` as a module.
- `frontend/src/main.ts`
  - Imports CSS and Leaflet’s CSS.
  - Builds the full page layout by setting `root.innerHTML`.
  - Wires UI event handlers (search inputs, tab switching, geolocation, map selection).

You can run the site in dev mode with:

- `cd frontend`
- `npm run dev`

Build/preview scripts exist in `frontend/package.json`:

- `npm run build`
- `npm run preview`

## 3) Frontend behavior: how “everything works”

### UI layout and selection concepts

The UI supports four selection “kinds”:

- `hotel`
- `poi` (point of interest / landmark)
- `location` (browser geolocation)
- `map` (user clicked coordinate on the map)

These kinds are defined in `frontend/src/domain/types.ts`:

- `SelectionKind = 'hotel' | 'location' | 'poi' | 'map'`
- `MapSelection` includes:
  - `latlng`
  - `label`
  - `kind`

The UI chip + map marker are always derived from a `MapSelection` object.

### The map layer (`createMap`)

Map rendering and marker behavior is encapsulated in:

- `frontend/src/map/mapController.ts`

`createMap(container, opts)` does:

1. Creates a Leaflet map on the given `container`.
2. Adds OpenStreetMap raster tiles:
   - `https://{s}.tile.openstreetmap.org/{z}/{x}/{y}.png`
3. Sets initial center and zoom to the provided `defaultCenter`.
4. Adds a single marker:
   - When you select something again, it updates the marker’s position and icon.
5. Attaches a `map.on('click')` listener:
   - Clicking the map generates a `MapSelection` of kind `map`.
   - It updates the marker popup + flies to the clicked coordinate.
   - It calls the `opts.onSelect(selection)` callback so `main.ts` can update UI state.

Marker icons are generated dynamically (inline SVG) to color-code selection kinds.

### The mock API layer (`mockApi.ts`)

All search results are currently generated by:

- `frontend/src/api/mockApi.ts`

Key exported functions:

- `searchHotels(query, limit)`
- `searchPois(query, limit)`
- `searchEverything(query, limit)`
  - returns a mixed list of `{ kind: 'hotel' | 'poi', hotel|poi }`

Important characteristics:

- Data is hardcoded arrays (`HOTELS`, `POIS`) inside `mockApi.ts`.
- Each “search” is asynchronous and simulates network delay with `sleep(...)`.
- There are TODO comments explicitly calling out that you will replace these with real endpoints later.

### Search UI and debouncing

In `frontend/src/main.ts`, there are two independent search flows:

1. **Hotel picker panel**
   - `hotelPickerInput` + `hotelPickerResults`
   - Input events are debounced (`debounce(..., 220)`).
   - Calls `searchHotels(query)`
   - Renders clickable “rows” created by `makeHotelRow(hotel)`
2. **Global search panel**
   - `globalSearchInput` + `globalSearchResults`
   - Debounced input calls `searchEverything(query)`
   - Renders “hotel” rows and “poi” rows with `makeHotelRow` / `makePoiRow`

When a user clicks a result row (or presses `Enter`/`Space` on focused rows), the corresponding `selectHotel(...)` / `selectPoi(...)` runs.

### How selection updates propagate

`main.ts` maintains a `currentSelection` variable and a `setChip(selection)` function that:

- Updates:
  - selection kind text
  - selection label
  - selection coordinates
  - HUD text on the map overlay
- Clears the chip if `selection` is `null`.

When selection changes, both the chip and map marker are updated:

- `map.setMarker(currentSelection, { flyTo: true })`

So “UI state” and “map marker state” are synchronized through the same `MapSelection`.

### Current location flow (geolocation)

The “Use my location” button uses the browser geolocation API:

- `navigator.geolocation.getCurrentPosition(...)`

On success:

- It builds a `MapSelection` of kind `location`.
- Updates the chip.
- Moves the map marker to that coordinate.

On failure:

- It shows a human-readable error in `locationStatus`.

### Tabs (Hotels vs Current location)

There are UI tabs:

- “Hotels”
- “Current location”

`setActiveTab('hotels' | 'location')` toggles:

- `hidden` state of the two panel sections (`panelHotels`, `panelLocation`)
- aria-selected attributes and opacity for accessibility cues.

## 5) Forecasting logic today (notebooks + CSV outputs)

The forecasting work lives in `notebooks/` and outputs processed CSVs in `data/processed/`.

### Data pipeline overview (by notebook)

1. `notebooks/01_collect_pois.ipynb`
   - Uses the Overpass API to query OpenStreetMap for Istanbul POIs.
   - Extracts points (lat/lon) and categorizes them using tag mappings like:
     - `tourism:attraction`, `historic:*`, `leisure=park`, etc.
2. `notebooks/01_collect_weather_data.ipynb`
   - Pulls historical weather for Istanbul (center coordinates) for multiple years.
   - Keeps daily temperature and precipitation signals.
3. `notebooks/02_preprocess_weather.ipynb`
   - Resamples daily weather into weekly aggregates:
     - `temp_max`, `temp_min`, `temp_avg` use `mean`
     - `precipitation` uses `sum`
   - Writes:
     - `data/processed/weather_istanbul_weekly.csv`
4. `notebooks/02_preprocess_google_trends.ipynb`
   - Loads exported Google Trends CSVs for multiple categories.
   - Concatenates and normalizes them into a single raw file with:
     - `date`, `trend_score`, `category`
5. `notebooks/04_build_crowd_index.ipynb`
   - Merges weekly trend demand with weekly weather.
   - Normalizes key variables (`trend_demand`, `temp_avg`, `precipitation`) with a `MinMaxScaler`.
   - Computes:
     - `crowd_index` using the formula
       - `0.5 * trend_demand + 0.3 * temp_avg + 0.2 * (1 - precipitation)`
     - `crowd_level` by splitting `crowd_index` into 3 quantiles:
       - labels: `Low`, `Medium`, `High`
6. `notebooks/05_addin_temporal_features.ipynb`
   - Adds time features derived from `date`:
     - `month`
     - `week_of_year`
   - Adds seasonal features (and one-hot encodes them into booleans like `season_spring`, `season_summer`, `season_winter`).
   - Produces:
     - `data/processed/model_dataset.csv`
7. `notebooks/06_add_holidays.ipynb`
   - Adds an `is_holiday` binary feature based on a hardcoded list of holiday weeks (fixed holidays + approximate Ramadan and sacrifice feast dates).
   - Writes:
     - `data/processed/model_dataset_with_holidays.csv`
8. `notebooks/07_random_forest_baseline.ipynb`
   - Trains a `RandomForestRegressor` baseline to predict `crowd_index`.
   - Uses time-series safe chronological split:
     - `X_train = first 80% of rows`
     - `X_test = last 20% of rows`
   - Model:
     - `RandomForestRegressor(n_estimators=200, max_depth=8, random_state=42)`
   - Reported metrics:
     - MAE: `0.013036646121430571`
     - RMSE: `0.017767267171817657`
     - R2: `0.9813415899857085`
   - Feature importance is plotted using `model.feature_importances_`.

### The processed dataset schema (what the model learns from)

`data/processed/model_dataset_with_holidays.csv` has columns:

- `date`
- `trend_demand`
- `temp_max`, `temp_min`, `temp_avg`
- `precipitation`
- `crowd_index`, `crowd_level` (targets / labels derived earlier)
- `month`, `week_of_year`
- `season_spring`, `season_summer`, `season_winter`
- `is_holiday`

In `07_random_forest_baseline.ipynb`, the model input `X` is built by dropping:

- `date`, `crowd_index`, `crowd_level`

So training features are essentially:

- demand + weather + time encoding + holidays

## 6) How the “future” should connect (UI <-> forecasting)

At the moment, the website shows selections and uses mock search results. The forecasting dataset is separate and not wired to UI predictions.

To connect them, the main missing piece is: a backend API that can:

1. Accept a **selection context** (hotel/POI coordinate, user-chosen time horizon, and possibly weather/time inputs).
2. Compute the model’s required features:
   - demand/trends signal (or a proxy for it)
   - weekly weather for the requested time (or a forecast weather)
   - derived time features (`month`, `week_of_year`, seasons) and `is_holiday`
3. Run the trained model and return:
   - predicted `crowd_index`
   - (optionally) predicted `crowd_level`
4. Return results so the frontend can:
   - show charts
   - color-code markers on the map
   - display “expected crowd level” for selected hotels/POIs

### What the frontend already hints at

`frontend/src/main.ts` and `frontend/src/api/mockApi.ts` include TODOs like:

- Replace `searchHotels`, `searchEverything` mock functions with real endpoints.
- Replace the mock data layer with real hotel/POI and search endpoints.

This is the seam you will use when you implement your backend.

## 7) Roadmap: what the next version will have

Below is a concrete roadmap that follows directly from what exists today.

### Phase 1 — Replace mock data with real APIs (small but important)

1. Implement real API endpoints in `backend/` (or a separate service).
   - `/hotels` (list)
   - `/hotels/search?q=...`
   - `/pois/search?q=...`
   - or a single `/search` that returns mixed hotel + POI results (mirroring `searchEverything`).
2. Update `frontend/src/api/mockApi.ts` to call real endpoints instead of hardcoded arrays.

UI behavior (tabs, selection chip, marker updates) can remain the same.

### Phase 2 — Add “crowd forecast” results to the selection workflow

1. Add a simple “time” control to the UI:
   - pick a target week/date (at minimum).
2. Add a “forecast panel” that shows:
   - predicted crowd index (number)
   - predicted crowd level (Low/Medium/High)
   - and possibly a trend line for upcoming weeks
3. Implement a backend prediction endpoint (example):
   - `POST /forecast` with:
     - selection kind + coordinates
     - requested target date/week
     - any needed forecast features
   - returns:
     - predicted `crowd_index`
     - derived `crowd_level`

Note: your current model is temporal (trained on Istanbul-level features like trends/weather/time), so the first iteration may treat all selected locations as “Istanbul-level predictions.” A later iteration can add spatial/district-specific modeling.

### Phase 3 — Make map visuals data-driven

1. When a POI/hotel is rendered, optionally show a predicted crowd badge next to it.
2. Color-code markers based on predicted crowd level for the chosen target week.
3. Enable “compare” mode:
   - compare multiple hotels/POIs side-by-side (helps decision-making).

### Phase 4 — Operationalize the modeling pipeline

1. Convert notebooks into reusable scripts or a pipeline:
   - data download/clean
   - feature creation
   - model training and evaluation
2. Store model artifacts (e.g. serialized model + preprocessing scalers).
3. Automate dataset generation so `data/processed/*` stays consistent with the model.

### Phase 5 — Quality and maintenance

1. Add tests for:
   - API contract correctness
   - feature generation logic
   - “prediction endpoint returns valid schema”
2. Add linting/formatting and CI to ensure frontend + backend stay compatible.
3. Add monitoring:
   - prediction latency
   - basic data drift checks for trends/weather inputs
